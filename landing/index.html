03 · Архитектурные решения

Что и почему выбрано — и чем заплачено

08 РЕШЕНИЙ
01

ELT внутри СУБД, а не ETL-скрипты снаружи

Вся загрузка и трансформация — хранимые процедуры SQL Server: BULK INSERT, валидация, SCD, пересчёт витрин. Снаружи — только конвертер Excel → CSV на Polars.

Цена решения: логика привязана к T-SQL; перенос на другую СУБД — переписывание.

02

Пять слоёв с разделением ответственности

staging — «как пришло», карантин — «что браковано и почему», ods — «чистая правда», dwh — аналитическая модель, datamart — готовые KPI. Каждый слой чинится изолированно.

Цена решения: больше кода и скриптов, зато ясные границы между этапами.

03

Kimball-звезда вместо Inmon и Data Vault

Один источник и конкретные отчёты (запасы/оборачиваемость) — звезда даёт результат быстрее 3NF-хранилища. Измерения согласованные: dim_date и dim_material общие для обоих фактов.

Цена решения: денормализация; для интеграции многих систем нужен был бы другой подход.

04

SCD точечно: склад — SCD2, материал — SCD1

Склад хранит историю изменений МОЛ и цеха с датами действия. Материалу история единиц измерения не нужна — только актуальная версия.

Цена решения: историю измерений материалов не ведём; пересмотр требований = пересборка измерения.

05

file_registry с SHA-256 — инкремент без дублей

Реестр хранит хеш каждого файла: новый — грузим, неизменённый — пропускаем, изменённый — перезагружаем. Повторный запуск ETL не меняет ни одного счётчика.

Цена решения: хеш считается для каждого файла при каждом прогоне загрузки.

06

Карантин вместо молчаливой потери строк

Строка с ошибкой не останавливает ETL: она уходит в карантин с исходными значениями и причиной. По ТЗ ошибочные данные не теряются и не маскируются.

Цена решения: карантин большой — 99,1% это свойства данных заказчика, а не дефект системы.

07

UNKNOWN-плейсхолдеры — паттерн Kimball

22 склада из обороток отсутствуют в справочнике. INNER JOIN терял бы ~10% фактов; вместо этого измерение получает служебную строку, а факт собирается через LEFT JOIN.

Цена решения: в отчётах появляются «неизвестные» склады, о которых нужно помнить.

08

Витрины и MoM считаются в SQL, не в BI

datamart предрасчитывает метрики и MoM (LAG по месяцам) для каждого уровня среза. Superset не выполняет тяжёлых агрегаций — это требование ТЗ.

Цена решения: витрины пересчитываются при каждой загрузке; ad-hoc-срезы — через SQL.

04 · Ограничения

Границы системы — честно

8 ПОЗИЦИЙ
данные заказчика

~46% строк цен — точные дубликаты в исходных файлах

Каждая вторая строка цен повторена в файлах несколько раз; ~79% строк складов — конфликтующие версии (разные МОЛ на одну дату). Система фиксирует их в карантине с причиной, в ODS идут только уникальные строки.

данные заказчика

22 кода складов отсутствуют в справочнике «Склады»

Для них создаются плейсхолдеры UNKNOWN (период 1900-01-01…9999-12-31). Ни одна строка фактов не теряется, но в отчётах нужно помнить про «неизвестные» склады.

масштаб

Учебные объёмы: ~5,9 млн строк, ETL 8–10 минут

Для продакшена понадобятся партиционирование фактов по дате, watermark-инкремент вместо пересчёта хешей и индексы под BI-фильтры. Слойная архитектура при этом не меняется.

архитектура

Кеш Superset запрещён ТЗ — каждый запрос идёт в БД

Live-запросы к витринам. Скорость отклика зависит от производительности БД и индексов витрин; витрины предрасчитаны, поэтому фильтры работают быстро.

архитектура

MoM отсутствует для самого первого месяца

Сравнивать не с чем — предыдущего периода нет. Это норма поведения, а не ошибка.

безопасность

Row Level Security ограничивает строки, но не обходит SQL Lab

Прямой SQL может обойти RLS-правила, поэтому доступ к SQL Lab на базе BI_DWH для не-админов закрывается на уровне ролей Superset.

архитектура

Один источник данных и один BI-клиент

Вход — Excel/CSV, витрины — для Superset. При интеграции многих систем потребовался бы Inmon или Data Vault; при нескольких BI-инструментах — отдельные слои экспорта.

данные

Цена берётся за период, а не «текущая»

Январь 2024 считается ценой января, а не ценой 2026-го — история не переписывается. Обратная сторона: «сегодняшняя» оценка старых периодов требует отдельного запроса.

06 · ETL-пайплайн

Девять шагов, один оркестратор

elt.sp_master_etl

Каждый шаг логируется в elt.elt_log — RUNNING → SUCCESS или ERROR с текстом. При падении: алерт в alert_queue (не зависит от почты) + письмо администратору через Database Mail.

00Загрузка в STAGINGelt.sp_load_staging_from_import

BULK INSERT файлов из /import. file_registry с SHA-256: новый файл грузится, неизменённый пропускается, изменённый перезагружается. STAGING — сырьё как пришло, без бизнес-логики.

csv → staging.* · etl.file_registry · статусы pending / loaded / failed

01Валидация оборотокelt.sp_validate_turnover

Типы, даты (Excel Serial и текст через elt.fn_parse_date), бизнес-правила. Брак — в карантин с причиной, корректные строки — в ODS.

staging.turnover → quarantine.turnover / ods.turnover

02Валидация ценelt.sp_validate_prices

Цена > 0, корректные даты; дубликаты внутри файлов — в карантин по ТЗ, в ODS идут только уникальные строки.

staging.prices → quarantine.prices / ods.prices

03Валидация складовelt.sp_validate_warehouses

Повторные и конфликтующие версии склада (разные МОЛ на одну дату) — в карантин; уникальные — в ODS.

staging.warehouses → quarantine.warehouses / ods.warehouses

04Измерение материаловdwh.sp_load_dim_material

SCD1: только актуальная единица измерения. 105 364 материала.

ods → dwh.dim_material · material_sk

05Измерение складовdwh.sp_load_dim_warehouse

SCD2: история МОЛ и цеха с датами действия; новая версия закрывает старую. Для 22 складов без снимка в справочнике — UNKNOWN-плейсхолдеры.

ods → dwh.dim_warehouse · warehouse_sk · date_from / date_to · is_current

06Факт остатковdwh.sp_load_fact_inventory

Зерно: период × склад × материал. Берётся последняя версия по дате выгрузки; LEFT JOIN + COALESCE на текущую версию склада — строка факта создаётся всегда.

ods → dwh.fact_inventory · 2 510 032 строк

07Факт ценdwh.sp_load_fact_prices

Зерно: период × материал. Последняя версия, UNIQUE-ключ по бизнес-зерну — дубликатов нет.

ods → dwh.fact_prices · 1 349 966 строк

08Пересчёт витринdatamart.sp_refresh_datamart

Метрики и MoM по 4 уровням срезов через LAG по месяцам. Витрины читает Superset без пересчёта в BI.

dwh → datamart.turnover_metrics · datamart.inventory_monthly

ПРИ СТАРТЕ

startup.sh: schema → agent → elt → datamart → views → mail, затем первичный ETL. Скрипты идемпотентны — повторный запуск безопасен; sqlcmd с флагом -b останавливает инициализацию при SQL-ошибке.

НОЧЬЮ

SQL Agent в 02:00: загрузка новых файлов + полный master ETL. Включение — переменной MSSQL_AGENT_ENABLED в .env.

ПРИ ОШИБКЕ

alert_queue (не зависит от почты) + письмо администратору через Database Mail; исходная ошибка не скрывается (THROW).
