01 · Архитектура

Слои данных: разделение ответственности

schema: staging · quarantine · ods · dwh · datamart · elt

staging

Сырой приём: данные из файлов фиксируются «как пришли», без бизнес-логики и приведения типов. Позволяет переиграть трансформацию, не трогая источник.

quarantine

Карантин: строки, не прошедшие валидацию, сохраняются с исходными значениями и причиной ошибки. Брак не теряется и не блокирует корректные данные.

ods

Очищенный слой: типизированные, валидированные строки с уникальными бизнес-ключами — «чистая правда» перед построением модели.

dwh

Аналитическая модель Кимбалла: факты и измерения, суррогатные ключи, SCD там, где нужна история. Источник для витрин.

datamart

Витрины: предрассчитанные метрики и MoM по уровням срезов. BI читает готовое, тяжёлые агрегации на стороне отображения запрещены по ТЗ.

elt

Служебный слой: реестр файлов (SHA-256), журнал запусков, очередь алертов. Инкрементальная загрузка и идемпотентность.

03 · Метрики

Четыре показателя + MoM по каждому

формулы сверены с данными · 0 несовпадений
Сумма запасов
Σ остаток_конец × цена_периода
сколько денег «заморожено» в товаре на конец месяца
Средний остаток
Σ (начало + конец)/2 × цена
сколько в среднем лежит на складе за период
Оборачиваемость, разы
расход_в_деньгах ÷ средний_остаток
сколько раз запас «обернулся» за месяц
Оборачиваемость, дни
30 × средний_остаток ÷ расход_в_деньгах
за сколько дней запас израсходуется при текущем темпе

MoM (Month-over-Month) — изменение показателя к предыдущему месяцу: (X_тек − X_пред) ÷ X_пред. MoM считается для каждого уровня среза отдельно — доли не «смешиваются» между уровнями.

04 · ETL-пайплайн

Девять шагов, один оркестратор

elt.sp_master_etl

Каждый шаг логируется в elt.elt_log — RUNNING → SUCCESS или ERROR с текстом. При падении: алерт в elt.alert_queue (не зависит от почты) + письмо администратору через Database Mail.

00Загрузка в STAGINGelt.sp_load_staging_from_import

BULK INSERT файлов из /import. Реестр elt.file_registry хранит SHA-256: новый файл грузится, неизменённый пропускается, изменённый перезагружается. STAGING — сырьё как пришло, без бизнес-логики.

csv → staging.* · file_registry · статусы pending / loaded / failed

01Валидация оборотокelt.sp_validate_turnover

Типы, даты (Excel Serial и текст через elt.fn_parse_date), бизнес-правила: остаток = начало + приход + расход, расход отрицательный. Брак — в карантин с причиной, корректные строки — в ODS.

staging.turnover → quarantine.turnover / ods.turnover

02Валидация ценelt.sp_validate_prices

Цена > 0, корректные даты; дубликаты внутри файлов — в карантин по ТЗ, в ODS идут только уникальные строки. Повторный запуск ничего не дублирует.

staging.prices → quarantine.prices / ods.prices

03Валидация складовelt.sp_validate_warehouses

Повторные и конфликтующие версии склада (разные МОЛ на одну дату) — в карантин; уникальные — в ODS.

staging.warehouses → quarantine.warehouses / ods.warehouses

04Измерение материаловdwh.sp_load_dim_material

SCD1: только актуальная единица измерения; история ЕИ не нужна для метрик.

ods → dwh.dim_material · material_sk

05Измерение складовdwh.sp_load_dim_warehouse

SCD2: история МОЛ и цеха с датами действия; новая версия закрывает старую. Для складов из фактов без снимка в справочнике создаются UNKNOWN-плейсхолдеры.

ods → dwh.dim_warehouse · warehouse_sk · date_from / date_to · is_current

06Факт остатковdwh.sp_load_fact_inventory

Зерно: период × склад × материал. По зерну берётся последняя версия выгрузки; склад цепляется к версии, актуальной на дату факта; LEFT JOIN + COALESCE — строка создаётся всегда. UNIQUE исключает дубликаты.

ods → dwh.fact_inventory

07Факт ценdwh.sp_load_fact_prices

Зерно: период × материал. Последняя версия цены, UNIQUE по бизнес-зерну — дубликатов нет.

ods → dwh.fact_prices

08Пересчёт витринdatamart.sp_refresh_datamart

Метрики и MoM по четырём уровням срезов через LAG по месяцам. Витрины читает Superset без пересчёта в BI (Live-запросы, кеш выключен по ТЗ).

dwh → datamart.turnover_metrics · datamart.inventory_monthly

05 · Запуск и надёжность

Развёртывание одной командой

$ cp .env.example .env
$ docker compose up -d --build
startup.sh: SQL Server → schema → agent → elt → datamart → views → mail → master ETL
✓ STARTUP INITIALIZATION SUCCESSFUL
→ http://localhost:8088 · admin / admin

Ночной прогон SQL Agent

Каждый день в 02:00: загрузка новых файлов + полный master ETL. SQL Agent — планировщик, бизнес-логика — в процедурах.

Логирование и алерты

Каждый шаг — RUNNING / SUCCESS / ERROR в elt.elt_log. При падении — alert_queue (в базе) и письмо администратору через Database Mail.

Идемпотентность

Повторный запуск не меняет счётчики слоёв: file_registry по хешам, NOT EXISTS-пропуски, UNIQUE-ключи, защита карантина от повторов.
