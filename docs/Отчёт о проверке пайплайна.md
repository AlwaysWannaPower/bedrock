# Отчёт о проверке пайплайна BI_DWH

Документ фиксирует результаты аудита всего ETL-пайплайна проекта **стадия → стадия** (по требованиям `Требования.md`, §21–25) и найденные/исправленные проблемы.

Дата проверки: 27.08.2026 (реальный прогон в Docker на ветке `test_deepseek_api`).

---

## 1. Что проверялось

```text
CSV (/import)
  ↓
STAGING          сырой слой (BULK INSERT, file_registry)
  ↓
VALIDATION       типы, даты, бизнес-правила
  ├── QUARANTINE ошибочные строки + причина
  └── ODS        очищенные данные
        ↓
DWH Kimball      DIM_DATE / DIM_MATERIAL / DIM_WAREHOUSE(SCD2)
                 FACT_INVENTORY / FACT_PRICES
        ↓
DATAMART         inventory_monthly / turnover_metrics + MoM
        ↓
Superset         (тонкий клиент, Live, без кеша)
```

## 3. Проблемы, найденные при аудите кода (до исправления)

### 3.1. Почтовый модуль «не включался» (критично)

**Симптом:** при перезапуске контейнера почта не работала, хотя вручную (через чат) всё настраивалось.

**Причины (найдены три):**

1. **`startup.sh` не передавал SMTP-переменные в sqlcmd.** Скрипт `sql/elt/11_elt_notify.sql` использует переменные подстановки `$(SMTP_SERVER)`, `$(SMTP_PORT)`, `$(ADMIN_EMAIL)` и т.д. sqlcmd подставляет их только через флаг `-v`. Без `-v` они превращались в пустые строки — аккаунт Database Mail создавался с пустым SMTP-сервером.
   **Исправление:** в `startup.sh` во все вызовы sqlcmd добавлены `-v SMTP_*` и `-v ADMIN_EMAIL` из переменных окружения (docker-compose берёт их из `.env`).

2. **Порядок стадий.** Раньше стадия `mail` шла ДО `elt`, хотя профиль `DWH Alerts` создаётся именно в `elt/11_elt_notify.sql`. Тестовое письмо не могло найти профиль.
   **Исправление:** порядок стадий: `schema → agent → elt → datamart → views → mail`.

3. **Процедура тестового письма создавалась, но никто её не вызывал.** Файл только объявлял `elt.sp_send_test_mail_in_first_up` — «модуль не включался», письмо не уходило.
   **Исправление:** в конце `sql/mail/01_sp_send_test_mail_in_first_up.sql` процедура вызывается; отправка защищена маркером `elt.mail_test_flag` (только один раз) и проверкой `ADMIN_EMAIL`.

4. **`sp_notify_admin` могла «замаскировать» ошибку ETL.** Если письмо не отправлялось, процедура бросала ошибку внутри CATCH master'а, и исходная ошибка ETL терялась.
   **Исправление:** внутри `sp_notify_admin` ошибка почты печатается (PRINT), но не пробрасывается. Факт падения ETL фиксируется в `elt.alert_queue` до вызова почты.

5. **Неверная проверка principal.** Проверка существования привязки профиля к роли `public` использовала `principal_sid = 0x01` (у `public` SID = 0x00, правильный `principal_id = 1`) — на повторном запуске попытка вставить дубликат.
   **Исправление:** проверка по `pp.principal_id = 1`.

### 3.2. Логирование ELT было слабым

- Логировались только 2 из 8 процедур пайплайна.
- `elt.elt_log` **удалялась и пересоздавалась при каждом старте контейнера** (DROP + CREATE в `06_elt_log.sql`) — история терялась.
- Не было алертов, независимых от почты.

**Исправление:**

- `06_elt_log.sql`: `CREATE TABLE IF NOT EXISTS` (без DROP); добавлена `elt.alert_queue`.
- Новый хелпер `elt.sp_log` (`sql/elt/10_sp_log.sql`) — единая запись RUNNING/SUCCESS/ERROR.
- `99_sp_master_etl.sql` логирует **каждый шаг** (0–8) со временем и текстом ошибки; при падении: `etl_log(ERROR)` → `alert_queue` → письмо → `THROW`.

### 3.3. Карантин стирался при перезапуске

`08_quarantine_tables.sql` удалял и создавал таблицы карантина (DROP + CREATE) — история отбракованных строк терялась.

**Исправление:** `IF NOT EXISTS` — таблицы создаются один раз, строки копятся инкрементально.

### 3.4. Индексы DIM_WAREHOUSE не были идемпотентными

`04_dwh_dimensions.sql` создавал индексы `IX_dim_warehouse_business_date` и `UX_dim_warehouse_current` без проверки существования — повторный деплой падал с «index already exists».

**Исправление:** оба индекса обёрнуты в `IF NOT EXISTS`.

### 3.5. sqlcmd «проглатывал» SQL-ошибки

Без флага `-b` sqlcmd печатает SQL-ошибки, но завершается кодом 0 — `startup.sh` писал ложный `SQL SCRIPT SUCCESS`, и пайплайн продолжал работу в сломанном состоянии.

**Исправление:** во все вызовы sqlcmd в `startup.sh` добавлен флаг `-b` (ошибка SQL → ненулевой exit code → `set -o pipefail` останавливает startup).

### 3.6. SQL Agent job выполнял только загрузку STAGING

Ночной job (`13_sql_agent_job.sql`) запускал только `sp_load_staging_from_import`, хотя по ТЗ §18 ночной запуск должен выполнять обе команды: загрузку staging **и** полный master ETL.

**Исправление:** job выполняет `sp_load_staging_from_import` + `sp_master_etl`.

### 3.7. ROWTERMINATOR для складов

`sp_bulk_warehouses_direct` использовал `ROWTERMINATOR = '0x0a'` (однобайтовый), тогда как файлы в UTF-16 требуют `0x0a00` (как у turnover/prices).

**Исправление:** единый `0x0a00` для всех трёх загрузчиков.

### 3.8. Дата только в числовом (Excel Serial) формате

Валидаторы захардкоженно читали даты как Excel Serial Date. Заказчик может прислать даты и в обычном текстовом виде.

**Исправление:** новая функция `elt.fn_parse_date` (`sql/elt/00_fn_parse_date.sql`) поддерживает оба формата:

```text
'45292'       -> 2024-01-01   (Excel Serial Date)
'45323.0'     -> 2024-02-01   (с дробной частью)
'2024-01-31'  -> 2024-01-31   (ISO)
'31.01.2024'  -> 2024-01-31   (dd.mm.yyyy)
'31/01/2024'  -> 2024-01-31   (dd/mm/yyyy)
```

Применена в `sp_validate_turnover`, `sp_validate_prices`, `sp_validate_warehouses`.

### 3.9. QUOTED_IDENTIFIER OFF ломал загрузку DIM_WAREHOUSE (ошибка 1934)

`sp_load_dim_warehouse` создавалась с `QUOTED_IDENTIFIER OFF` (default sqlcmd). INSERT в таблицу с **фильтрованным индексом** (`UX_dim_warehouse_current`) требует `QUOTED_IDENTIFIER ON` — падало с ошибкой 1934. Из-за этого измерение складов было пустым, а факты не собирались вовсе.

**Исправление:** во все файлы процедур добавлены `SET ANSI_NULLS ON; SET QUOTED_IDENTIFIER ON;` перед `CREATE OR ALTER`.

### 3.10. Потеря ~10% фактов: склады без снимка в справочнике

В оборотках встречаются коды складов, которых **нет** в файле «Склады» (22 склада: 115H, 240B, … — ~250 тыс. строк). `sp_load_fact_inventory` использовал `INNER JOIN` по измерению складов → такие строки **молча терялись**.

**Исправление (паттерн Kimball «unknown member»):**
- `sp_load_dim_warehouse` создаёт для каждого недостающего склада плейсхолдер: `warehouse_type = 'UNKNOWN'`, период 1900-01-01…9999-12-31;
- `sp_load_fact_inventory` использует `LEFT JOIN` + `COALESCE` на текущую версию склада — строка факта создаётся всегда.

После исправления `fact_inventory` = 2 510 032 строк (было 2 260 590).

### 3.11. Идемпотентность валидаторов цен/складов

При повторном запуске `sp_validate_prices`/`sp_validate_warehouses` помечали **все** старые строки staging как «Дубликат строки в ODS» и заново сбрасывали их в карантин (затопление карантина при каждом прогоне).

**Исправление:** проверка «уже есть в ODS» заменена на `NOT EXISTS`-пропуск (как в оборотках); добавлена защита от повторной вставки `load_id` в карантин. Повторный запуск ETL теперь ничего не дублирует.

### 3.12. Ошибки в витринах, найденные реальным прогоном

- `agg_key` уровня `shop` = `directorate + ' | ' + shop_code` давал `NULL` при NULL-дирекции (конкатенация с NULL) → `ISNULL` в ключе;
- MoM оборачиваемости: деление на 0 при нулевом прошлом значении (ошибка 8134) → добавлены проверки `= 0`.

### 4.6. Проверка формул витрин (повторный контроль)

Каждая формула сверена с фактическими данными витрин (август 2026, после
пересчёта):

| Формула | Несовпадений | Комментарий |
|---|---|---|
| `stock_value = balance_end × price` | **0** | точное равенство |
| `expense_value = \|expense_qty\| × price` | **0** | точное равенство |
| `avg_stock_value = avg_qty × price` | **0** | после фикса округления (см. ниже) |
| `turnover_ratio = expense_value / avg_stock_value` | **0** | с допуском на округление до 4 знаков |
| `turnover_days = 30 × avg_stock_value / expense_value` | **0** | с допуском на округление до 2 знаков |
| `mom_X = (X_тек − X_пред) / X_пред` | **0** | с допуском на округление до 4 знаков |

Найден и исправлен нюанс: `avg_stock_value` считался по НЕокруглённому
среднему остатку, из-за чего в 0,16% строк не совпадал с `avg_qty × price`
(расхождение в копейки). Исправлено в `sql/datamart/10_sp_refresh_datamart.sql`:
средний остаток округляется до 2 знаков (`ROUND(..., 2)`) до умножения на цену.

**Контрольные цифры компании (для сравнения с дашбордом):**

```text
Месячная сумма запасов:   1 208–1 762 млн ₽ (миллиарды, НЕ триллионы)
Итог за 24 месяца:        ~37,6 млрд ₽ (сумма месячных остатков)
Сумма по ВСЕМ уровням:    ~144,6 млрд ₽ (если в BI не фильтровать agg_level и месяц)
```

> «Триллионы» на дашборде — артефакт настройки Superset (нет фильтра месяца
> и/или уровня), а не дефект витрин. Исправляется фильтрами и метриками `mom_*`.
