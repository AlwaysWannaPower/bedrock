# Дашборд: фильтры, скопы и разделение доступа

Три вопроса: как работают фильтры дашборда, какие у них «скопы» (какие чарты
они затрагивают), и как сделать так, чтобы каждый пользователь видел **только
свою зону ответственности** (роли из ТЗ).

---

## 1. Как работает фильтр дашборда

Фильтр дашборда (native filter) = **`WHERE` к витрине**.

```text
Фильтр «Дирекция = Дирекция по производству»
  ↓
SQL: SELECT ... FROM datamart.turnover_metrics
     WHERE directorate = 'Дирекция по производству'
```

Superset не пересчитывает метрики — он **фильтрует готовые строки** витрины
и рисует их. Поэтому важно понимать, какая колонка что значит:

| Колонка фильтра | Что фильтрует | Кто выбирает |
|---|---|---|
| `month_key` | период (202401…202512) | все |
| `agg_level` | уровень среза: company/directorate/shop/warehouse | роль |
| `directorate` | дирекцию | директор |
| `shop_code` | цех | начальник цеха |
| `warehouse_code` | склад | начальник склада |

## 2. Какие фильтры создать (набор по умолчанию)

На дашборде в **Edit dashboard → Filters → + Filter** создай 5 фильтров:

| Фильтр | Колонка | Тип | Default |
|---|---|---|---|
| Роль | `agg_level` | Select (одиночный!) | `company` |
| Месяц | `month_key` | Select (одиночный!) | `202512` |
| Дирекция | `directorate` | Select | — |
| Цех | `shop_code` | Select | — |
| Склад | `warehouse_code` | Select | — |

**Откуда фильтры берут список значений (важно):**
- Фильтры **«Роль»** и **«Месяц»** берут значения из `vw_turnover_metrics`
  (значения `agg_level`, `month_key` — без мусора);
- Фильтры **«Дирекция», «Цех», «Склад»** берут значения из справочника
  `vw_warehouse_hierarchy` (реальные склады уровня `warehouse`). Это сделано,
  чтобы в списках не появлялись «пустые» варианты: в единой витрине
  `turnover_metrics` строки уровня `company`/`directorate`/`shop` не принадлежат
  складу/цеху (пустые значения), а у складов-плейсхолдеров UNKNOWN
  (коды из обороток, отсутствующие в реестре «Склады») атрибуты заменены на
  явные «Не определена» / «—» (см. `sql/elt/07_sp_load_dim_warehouse.sql`,
  `sql/datamart/10_sp_refresh_datamart.sql`).

**Почему «одиночный»?** Если включён множественный выбор и выбраны все
значения — фильтр ничего не ограничивает, и KPI суммируют всё подряд
(«триллионы»). Одиночный выбор + значение по умолчанию = всегда виден
один осмысленный срез.

## 3. Скопы (scope) — какие чарты затрагивает фильтр

У каждого фильтра есть **Scope**: список чартов, на которые он действует.
Правильная карта скопов для нашего дашборда:

| Фильтр | KPI (8 шт) | MoM (4 шт) | Тренды (2 шт) | Структура (pie/bar/table) |
|---|---|---|---|---|
| **Роль** (`agg_level`) | ✅ | ✅ | ✅ | ✅ |
| **Месяц** (`month_key`) | ✅ | ✅ | ❌ (все месяцы) | ✅ |
| **Дирекция** | ❌ | ❌ | ❌ | ✅ |
| **Цех** | ❌ | ❌ | ❌ | ✅ |
| **Склад** | ❌ | ❌ | ❌ | ✅ |

Логика:

- **Роль и Месяц** управляют KPI/MoM — потому что KPI = «одна строка»
  (уровень роли × месяц).
- **Тренды** показывают все месяцы → исключаем их из фильтра «Месяц»
  (в Scope фильтра «Месяц» снимаем галку с трендов).
- **Дирекция/Цех/Склад** нужны только структуре (pie/bar/table) — они
  «уточняют» структуру внутри выбранной роли. KPI они не трогают, иначе
  получатся конфликты (например, КПИ=company + дирекция → пусто).

**Как настроить Scope в Superset:** фильтр → ⚙ (Edit filter) → раздел
**Scope** → список чартов с галками → поставь/сними нужные → Save.

**Как настроить каскад (иерархию):** у фильтра «Цех» в настройках
**Parent filter = Дирекция**; у «Склада» **Parent filter = Цех**.
Тогда выбор дирекции сузит список цехов, выбор цеха — список складов.

## 4. Режим «роли» на дашборде (демо для защиты)

Один дашборд, роль = комбинация фильтров:

| Роль | Роль (agg_level) | Дирекция | Цех | Склад |
|---|---|---|---|---|
| Генеральный директор | `company` | — | — | — |
| Директор по производству | `directorate` | Дирекция по производству | — | — |
| Директор по закупкам | `directorate` | Дирекция по закупкам и логистике | — | — |
| Начальник цеха | `shop` | своя | свой | — |
| Начальник склада | `warehouse` | — | — | свой |
| Менеджер по закупкам | `directorate` | Дирекция по закупкам и логистике | — | — |

**Важно:** у KPI/MoM-чартов **не должно быть** собственного жёсткого фильтра
`agg_level='company'` (иначе фильтр «Роль» не сможет переключить их на
дирекцию/склад). Убери его, пусть уровнем управляет фильтр «Роль»
(по умолчанию — company).

Демонстрация на защите: выставил фильтры роли → скриншот → сброс в default.

## 5. Реальное разделение доступа (каждый видит свою зону)

Фильтры — это «вежливая» схема: любой пользователь может снять фильтр и
увидеть всё. Настоящее ограничение строк делает **Row Level Security (RLS)**
в Superset: пользователю физически не приходят строки вне его зоны.

### 5.1. Схема «роль → правило RLS»

| Роль пользователя | RLS-правило (WHERE к витринам) |
|---|---|
| Генеральный директор | (нет правил → видит всё) |
| Директор по производству | `directorate = 'Дирекция по производству'` |
| Директор по закупкам | `directorate = 'Дирекция по закупкам и логистике'` |
| Начальник цеха | `shop_code = '<код цеха>'` |
| Начальник склада | `warehouse_code = '<код склада>'` |
| Менеджер по закупкам | `directorate = 'Дирекция по закупкам и логистике'` |

### 5.2. Шаги в Superset

1. **Создать роли:** Settings → List Roles → + Role.
   Имена: `Генеральный директор`, `Директор по производству`,
   `Начальник цеха`, `Начальник склада`, `Менеджер по закупкам`.
   В каждую роль добавь базовую роль **Gamma** (или минимальные права
   на чтение дашборда и витрин).

2. **Создать пользователей:** Settings → List Users → + User
   (username, пароль, назначить роль).

3. **Создать RLS-правила:** Security → Row Level Security → + Add.
   Для каждой ограниченной роли:
   - **Tables**: `vw_turnover_metrics`, `vw_inventory_monthly`,
     `vw_warehouse_hierarchy` (все три — иначе обойдут через другую витрину);
   - **Clause**: например `directorate = 'Дирекция по производству'`;
   - **Roles**: роль пользователя.

   Генеральному директору правило НЕ создаём — видит всё.

4. **Доступ к дашборду:** у роли должны быть права на дашборд и чарты
   (Settings → List Roles → роль → Permissions → добавить нужные пункты
   меню Dashboard/Charts). Без этого пользователь не увидит дашборд вовсе.

5. **Проверка:** войди под пользователем-«начальником склада» — в KPI,
   графиках и фильтрах будут только его строки; чужие склады в фильтре
   «Склад» не появятся.

### 5.3. Важные оговорки

- **SQL Lab.** RLS применяется к запросам чартов (и обычно к SQL Lab по этим
  datasets). Для демо лучше не давать не-админам доступ к SQL Lab на базе
  `BI_DWH` — иначе можно «уйти в обход» прямым SQL.
- **Одно правило на склад.** Если складов много, правило с фиксированным
  `warehouse_code` нужно на каждый склад. Вариант — ограничивать по `shop_code`
  или `directorate` (уровень выше), либо экспериментировать с полем
  **Group By** в правиле RLS (создаёт правила по значениям колонки).
- **RLS — это про строки, а не про права.** Кто имеет право вообще видеть
  дашборд — задаётся ролями и permissions отдельно.

### 5.4. Итоговый список созданных правил RLS (04.09.2026)

Создано в Superset (Security → Row Level Security). Каждое правило применено
ко **всем трём витринам** (`vw_turnover_metrics`, `vw_inventory_monthly`,
`vw_warehouse_hierarchy`), иначе данные можно было бы «обойти» через другую
витрину.

| Роль (Superset) | RLS-правило (WHERE) | Кто видит |
|---|---|---|
| `Генеральный директор` | — (правила нет) | все строки всех уровней |
| `Директор по производству` | `directorate = 'Дирекция по производству'` | только свою дирекцию |
| `Начальник цеха` | `shop_code = '280'` | только свой цех (и его склады) |
| `Начальник склада` | `warehouse_code = '0109'` | только свой склад |
| `Менеджер по закупкам` | `directorate = 'Дирекция по закупкам и логистике'` | только дирекцию закупок |

Привязка демо-пользователей к ролям:

| Пользователь | Роль |
|---|---|
| `gen_dir@gmail.com` | Генеральный директор |
| `dir_directorate@gmail.com` | Директор по производству |
| `shop@gmail.com` | Начальник цеха (цех 280) |
| `warehouse@gmail.com` | Начальник склада (склад 0109) |

Проверка RLS: войти под `shop@gmail.com` — в KPI/графиках и фильтре «Цех»
будут только цех 280; под `warehouse@gmail.com` — только склад 0109;
под `gen_dir@gmail.com` — все данные.

> Для «Начальника цеха»/«Начальника склада» с другими зонами создаются
> отдельные правила с другим `shop_code`/`warehouse_code`, либо правило
> с Group By по колонке (одно правило на все значения роли).

> ⚠️ **Кириллица в правиле — с префиксом `N`.** Правило вставляется в SQL-запрос
> как есть, а колонки (`directorate`, `shop_code`…) — `NVARCHAR`. Если написать
> `directorate = 'Дирекция по производству'` (без `N`), драйвер Superset (pymssql)
> сравнивает varchar-литерал с NVARCHAR-колонкой и получает **0 строк** (данные
> «пропадают»). Правильно: `directorate = N'Дирекция по производству'`.
> Для числовых зон (`shop_code = '280'`, `warehouse_code = '0109'`) это не критично,
> но для единообразия тоже можно писать `N'...'`.

> ⚠️ **RLS + уровень среза.** Правило RLS режет строки по зоне, но **не задаёт
> `agg_level`**. Поэтому под ролью KPI корректно считаются после выбора уровня
> в фильтре «Уровень (роль)» (директор → `directorate`, цех → `shop`,
> склад → `warehouse`, ген. директор → `company`).

## 6. Ответ на вопрос «по ТЗ это обязательно?»

ТЗ разрешает **оба** варианта:

> «Дашборд может быть единым для всех с настройкой фильтров по ролям
> или отдельным для каждой роли — на усмотрение исполнителя.»

Поэтому для защиты достаточно:
- единый дашборд + фильтры-роли (раздел 4) — **обязательно**;
- RLS (раздел 5) — **опционально**, как «вишенка» и ответ на вопрос
  «а если бы доступы были по-настоящему разные?».
