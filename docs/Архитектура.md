# Архитектура проекта

## 1. Общее устройство

Проект реализует конвейер подготовки и аналитической обработки данных от исходных Excel-файлов до BI-отчётности.

Основной поток данных:

```text
            EXCEL
              │
              ▼
        CSV CONVERTER
        Python + Polars
        XLSX → CSV
              │
              ▼
            STAGING
        Исходные данные
              │
              ▼
          VALIDATION
     Проверка качества данных
              │
  ┌───────────├──────────────────┐
  ▼                               ▼
QUARANTINE                       ODS
Некорректные                   Очищенные
данные                          данные
                                  │
                                  ▼
                              DWH KIMBALL
                                  │
            ┌─────────────────────┴───────────────┐
            ▼                                     ▼
       DIMENSIONS                               FACTS
            │                                     │
   ┌────────┼────────┐                       ┌────┴────┐
   ▼        ▼        ▼                       ▼         ▼
 date    material  warehouse             inventory    prices
                   SCD Type 2
                        
            ┴─────────────────────────────────────────┴
                                  │
                                  ▼
                              Superset
                                  │
                                  ▼
                              BI / отчёты
```

---

## 2. Этапы обработки данных

### 2.1. Исходные данные

Источником данных являются Excel-файлы (`.xlsx`).

Файлы содержат исходные операционные данные, которые необходимо загрузить в хранилище и подготовить для последующего аналитического использования.

```text
/data/prices
/data/turnover
/data/warehouse
```

---

### 2.2. Конвертация Excel → CSV

Для конвертации файла формата `.xlsx` -->`csv` используется отдельный Python-скрипт на базе **Polars**.
Скрипт выполняет:

* поиск Excel-файлов;
* чтение `.xlsx`;
* сохранение результата в CSV;
* (структура и данные не меняются)

```text
Пример:
/data/prices
      │
      ▼
Python + Polars
      │
      ▼
/data/csv/prices
```

CSV используется как промежуточный файловый формат между исходными Excel-файлами и SQL Server.

---

## 3. STAGING

`staging` — сырой слой данных.

На этом этапе данные загружаются в SQL Server максимально близко к исходному представлению.

Основная задача слоя — **зафиксировать поступившие данные до выполнения бизнес-преобразований**.

```text
CSV
 │
 ▼
SQL Server
 │
 ▼
staging.raw
```

В `staging` не будет выполняться сложная бизнес-логика. Слой предназначен прежде всего для первичной загрузки и  проверки данных в следующих слоях.

---

## 4. VALIDATION

После загрузки в `staging` данные проходят проверки качества.

Проверяются, в частности:

* обязательные поля;
* типы данных;
* корректность дат;
* числовые значения;
* наличие необходимых связей;
* дубликаты;
* бизнес-ограничения.

Результат проверки разделяет записи на два потока:

```text
                STAGING
                   │
                   ▼
                VALIDATION
              /            \
             /              \
            ▼                ▼
      QUARANTINE            ODS
     некорректные        корректные
        данные             данные
```

---

## 5. QUARANTINE

`quarantine` — слой изоляции некорректных данных.

Записи, которые не проходят проверки качества, не должны блокировать обработку корректных данных.

Такие записи помещаются в карантин вместе с информацией, необходимой для последующего анализа причины ошибки.

Примеры причин попадания в карантин:

* некорректная дата;
* невозможное числовое значение;
* отсутствие обязательного значения;
* нарушение ограничения;
* неизвестный идентификатор;
* нарушение бизнес-правила

Карантин позволяет сохранить исходную запись и одновременно продолжить обработку остальных данных.

---

## 6. ODS

`ods` — промежуточный слой очищенных.

На этом этапе выполняются преобразования, необходимые для подготовки данных к аналитической модели:

* очистка;
  * приведение типов;           
* стандартизация значений;
* устранение технических особенностей исходных файлов;
* подготовка ключей;
* выполнение необходимых бизнес-преобразований.

В результате `ods` содержит данные, которые уже соответствуют установленным правилам качества и готовы к загрузке в DWH.

```text
                STAGING
                   │
                   ▼
               VALIDATION
                   │
                   ▼
                  ODS
                   │
                   ▼
                  DWH
```

---

## 7. DWH — модель Kimball

`dwh` — основное аналитическое хранилище данных.

Модель строится по методологии **Kimball** и использует схему «звезда».

Основные компоненты:

* таблицы фактов (`facts`);
* таблицы измерений (`dimensions`).

```text
                             DWH
                              │
          ┌───────────────────┴─────────────────────┐
          │                                         │
          ▼                                         ▼
     DIMENSIONS                                   FACTS
          │                                         │
    ┌─────┼───────────┐                        ┌────┴────┐
    ▼     ▼           ▼                        ▼         ▼
  date  material  warehouse                 inventory   prices
```

### Измерения

Основные измерения проекта:

* `date` — календарное измерение;
* `material` — материалы;
* `warehouse` — склады.

Для изменяющихся атрибутов измерений используется **SCD Type 2**, позволяющий сохранять историю изменений.

### Факты

Основные факты проекта:

* `inventory` — данные об остатках / движении запасов;
* `prices` — данные о ценах.

Факты содержат числовые показатели и ссылки на соответствующие измерения.

---

## 8. DATAMART

`datamart` — слой аналитических витрин.

Витрины предназначены для непосредственного использования BI-инструментами.

В отличие от DWH, витрины могут содержать уже агрегированные или специально подготовленные наборы данных, ориентированные на конкретные аналитические задачи.

```text
            DWH
             │
             ▼
          DATAMART
             │
             ▼
             BI
```

Использование витрин позволяет не переносить сложную логику преобразований непосредственно в BI-запросы.

---

## 9. ELT-служебный слой

`elt` — технический слой, содержащий объекты, необходимые для управления процессом загрузки.

В него входят:

* реестр обработанных файлов;
* журналы запусков;
* статусы загрузок;
* информация об ошибках;
* технические идентификаторы загрузок;
* служебная информация ETL/ELT-процессов.

Одним из ключевых механизмов является `file_registry`.

```text
CSV
 │
 ▼
file_registry
 │
 ├── новый файл → обработать
 │
 └── уже обработан → пропустить
```

Это позволяет реализовать **идемпотентную и инкрементальную загрузку**.

---

## 10. Загрузка файлов в SQL Server

SQL Server получает список файлов из каталога импорта.

Для обнаружения файлов используется `xp_dirtree`.

Общий процесс:

```text
/data/csv/..
     │
     ▼
 xp_dirtree
     │
     ▼
поиск CSV-файлов
     │
     ▼
file_registry
     │
     ▼
проверка файла
     │
     ├── уже загружен → пропуск
     │
     └── новый файл
             │
             ▼
        BULK INSERT
             │
             ▼
       staging.raw
```

`BULK INSERT` используется для непосредственной загрузки CSV-файлов в SQL Server.

# 12. Архитектура запуска SQL Server

Проект запускается в контейнере.

Точкой входа является `startup.sh`.

Общий процесс запуска:

```text
Docker
  │
  ▼
startup.sh
  │
  ▼
запуск SQL Server
в фоновом режиме (&)
  │
  ▼
сохранение PID
  │
  ▼
ожидание готовности SQL Server
  │
  ▼
периодическая проверка
SELECT 1
  │
  ▼
SQL Server готов
  │
  ▼
выполнение SQL-скриптов
  │
  ▼
загрузка данных
  │
  ▼
ожидание SQL Server
```

## 13. Инициализация базы данных

После того как SQL Server становится доступен, `startup.sh` последовательно выполняет SQL-скрипты проекта.

Логическая последовательность:

```text
SQL Server готов
      │
      ▼
┌─────────────────────────┐
│ STAGE                   │
│                         │
│ schema → *.sql          │
│ elt    → *.sql          │
│ views  → *.sql          │
└─────────────────────────┘
      │
      ▼
 sp_etl_master
 (Создание схем,
 затем последовательные
 elt скрипты)
      │
      ▼
DWH загружен
```

Таким образом, создание структуры базы данных и последующая загрузка данных выполняются автоматически при запуске контейнера.

# 14. Назначение схем базы данных

| Схема        | Назначение                                                                                |
| ------------ | ----------------------------------------------------------------------------------------- |
| `staging`    | Сырой слой. Данные, загруженные из исходных файлов практически без преобразований.        |
| `ods`        | Промежуточный слой очищенных, нормализованных и подготовленных данных.                    |
| `dwh`        | Основное аналитическое хранилище с моделью Kimball: факты и измерения.                    |
| `quarantine` | Хранение записей, не прошедших проверки качества данных.                                  |
| `elt`        | Служебные объекты: реестры файлов, журналы, статусы и техническая информация о загрузках. |
| `datamart`   | Аналитические витрины, подготовленные для BI и Superset.                                  |

Схемы используются не только для логической группировки таблиц.

Они разделяют ответственность между различными этапами обработки данных и позволяют явно определить границы каждого слоя системы.

# 15. Идемпотентность

SQL-скрипты создания структуры проекта должны быть идемпотентными.

Это означает, что повторный запуск скрипта не должен приводить к ошибке из-за уже существующих объектов.

Например:

```text
если schema существует
    → не создавать повторно

если table существует
    → не создавать повторно

если procedure существует
    → обновить через CREATE OR ALTER
```

Идемпотентность позволяет:

* повторно разворачивать проект;
* пересоздавать контейнер;
* безопасно выполнять initialization-скрипты;
* восстанавливать окружение после удаления базы;
* использовать одинаковую процедуру развёртывания для разных окружений.

Для загрузки данных аналогичный принцип реализуется через `file_registry`: уже обработанные файлы не должны загружаться повторно.

# 16. Основные принципы архитектуры

Архитектура проекта основана на следующих принципах:

1. **Разделение слоёв** — каждый слой отвечает за отдельную стадию обработки данных.
2. **Сохранение исходных данных** — данные сначала фиксируются в `staging`, после чего преобразуются.
3. **Контроль качества** — некорректные записи отделяются от корректных и помещаются в `quarantine`.
4. **Разделение очистки и аналитической модели** — подготовка данных выполняется в `ods`, а аналитическая модель реализуется в `dwh`.
5. **Kimball-модель** — DWH организован вокруг фактов и измерений.
6. **Историчность** — для изменяющихся измерений используется SCD Type 2.
7. **Инкрементальная загрузка** — обработка файлов контролируется через `file_registry`.
8. **Идемпотентность** — повторный запуск инфраструктурных и ETL-операций не должен приводить к неконтролируемому дублированию данных.
9. **Автоматизация развёртывания** — создание структуры БД и первичная загрузка выполняются автоматически при запуске контейнера.
10. **Разделение DWH и BI** — Superset работает поверх подготовленных DWH/Datamart-данных и не отвечает за основную бизнес-логику подготовки данных.
