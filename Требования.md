# Требования проекта BI_DWH

## 1. Назначение документа

Этот файл является контрольным документом для разработки и проверки SQL-кода проекта BI_DWH.

Цель проверки: убедиться, что фактическая реализация SQL соответствует ТЗ, архитектуре проекта и заданному ETL-процессу.

Проверяющий должен проверять не только наличие процедур и таблиц, но и фактическую логику их работы.

---

# 2. Основное ТЗ

## 2.1 Первоначальная и инкрементальная загрузка

Система должна обеспечивать:

1. Первоначальную загрузку всех исходных файлов.
2. Инкрементальную загрузку новых данных.
3. Обработку изменённых файлов/данных.
4. Повторный запуск ETL не должен приводить к появлению дубликатов.
5. Уже успешно загруженные файлы не должны загружаться повторно без причины.
6. Ошибочные данные не должны останавливать обработку всего набора данных, если ошибка относится только к отдельным строкам.

### Что проверять

Проверить:

- `etl.file_registry`;
- процедуру обнаружения файлов;
- механизм определения нового/изменённого файла;
- статус загрузки файла;
- защиту от повторной загрузки;
- отсутствие дублей после повторного запуска;
- обработку изменённого файла.

---

# 3. Архитектура данных

Проект использует следующие логические слои:

```text
Файлы
  ↓
STAGING
  ↓
QUARANTINE + ODS
  ↓
DWH
  ↓
DATAMART
```

## 3.1 STAGING

Назначение:

- принять данные из исходного CSV;
- сохранить исходные значения;
- не выполнять бизнес-валидацию;
- не выполнять очистку данных.

STAGING является сырым слоем.

Здесь допустимы значения, которые впоследствии окажутся ошибочными.

### Проверять

Нельзя выполнять в STAGING:

- бизнес-проверки;
- исправление значений;
- удаление ошибочных строк;
- преобразование бизнес-смысла данных.

---

# 4. Загрузка файлов

Основная процедура:

```sql
EXEC BI_DWH.etl.sp_load_staging_from_import;
```

Она отвечает за загрузку файлов из каталогов `/import`.

Общий поток:

```text
каталог /import
      ↓
обнаружение CSV
      ↓
etl.file_registry
      ↓
BULK INSERT
      ↓
staging.*
```

## 4.1 Обнаружение файлов

Для обнаружения файлов используется SQL Server.

Проверяющий должен установить:

1. Из какого каталога читаются файлы.
2. Как определяется список CSV.
3. Как определяется имя файла.
4. Как формируется полный путь к файлу.
5. Как проверяется наличие файла в `etl.file_registry`.

---

# 5. Реестр файлов

Таблица:

```sql
etl.file_registry
```

Назначение — контроль состояния каждого исходного файла.

Минимально необходимая информация:

- идентификатор файла;
- тип источника;
- имя файла;
- путь к файлу;
- статус;
- количество загруженных строк;
- время загрузки;
- текст ошибки.

Пример статусов:

```text
pending
loaded
failed
```

## 5.1 Требования к реестру

Реестр должен позволять определить:

- файл новый;
- файл уже успешно загружен;
- файл завершился ошибкой;
- файл был изменён.

### Важное требование

Проверка только по `file_name` недостаточна для полноценного выполнения требования:

> загружаются только новые и измененные данные.

Если файл с тем же именем был изменён, система должна иметь возможность определить это.

Для этого рекомендуется хранить признак версии файла, например:

- хеш содержимого;
- размер + время изменения;
- другой надёжный fingerprint.

При использовании хеша проверяющий должен отдельно оценить стоимость его вычисления и момент вычисления.

---

# 6. BULK INSERT

Для загрузки CSV используется:

```sql
BULK INSERT
```

Назначение:

```text
CSV → SQL Server → STAGING
```

BULK INSERT должен использовать корректные параметры конкретного формата CSV:

- разделитель полей;
- разделитель строк;
- кодировку;
- пропуск заголовка;
- кавычки, если они используются.

## 6.1 Типы данных

Нужно учитывать риск:

```text
CSV
 ↓
типизированная STAGING-таблица
 ↓
ошибка BULK INSERT
```

Если SQL Server не может преобразовать значение CSV в тип колонки, BULK INSERT может завершиться ошибкой.

Поэтому выбор типов STAGING является архитектурным решением.

Проверяющий должен убедиться, что выбранная стратегия соответствует ТЗ и требованиям к карантину.

---

# 7. QUARANTINE

Карантин предназначен для строк, которые невозможно или неправильно использовать в ODS.

Общий поток:

```text
STAGING
   ↓
валидация
   ├── ошибка → QUARANTINE
   │
   └── корректная строка → ODS
```

## 7.1 Требования

Для ошибочной строки необходимо сохранить:

- идентификатор исходной строки;
- имя файла;
- исходные значения;
- причину ошибки.

Ошибка должна быть диагностируемой.

Пример:

```text
Некорректная start_date
Некорректный material_id
price <= 0
start_date > end_date
Дубликат строки
```

---

# 8. ODS

ODS содержит:

- очищенные;
- типизированные;
- валидированные;
- пригодные для дальнейшей обработки данные.

Общий поток:

```text
STAGING
   ↓
проверки
   ↓
ODS
```

ODS не должен содержать строки, которые были отправлены в карантин.

---

# 9. Валидация

Для каждой сущности должны быть определены:

### Технические проверки

- корректность типов;
- отсутствие невозможных преобразований;
- корректность дат;
- корректность числовых значений.

### Бизнес-проверки

Проверять только те правила, которые определены требованиями проекта.

Пример:

```text
start_date <= end_date
material_id > 0
price > 0
```

Если правило не определено ТЗ, его нельзя молча добавлять как обязательное бизнес-правило.

---

# 10. Дубликаты

Необходимо различать:

### 10.1 Дубликат внутри входного файла

Одна и та же бизнес-запись встречается несколько раз.

### 10.2 Повторная загрузка файла

Один и тот же файл был обработан повторно.

### 10.3 Новая версия данных

Тот же бизнес-объект имеет новую дату/версию выгрузки.

Это разные ситуации и они должны обрабатываться разной логикой.

---

# 11. DWH

DWH реализует модель Kimball:

```text
                 DIM_DATE
                    │
                    │
DIM_WAREHOUSE ─ FACT_INVENTORY ─ DIM_MATERIAL
                    │
                    │
               другие измерения
```

Для проекта используются:

- измерения;
- факты;
- суррогатные ключи;
- бизнес-ключи.

---

# 12. Измерения

## 12.1 DIM_DATE

Должна содержать уникальную дату.

Проверка:

```sql
SELECT full_date, COUNT(*)
FROM dwh.dim_date
GROUP BY full_date
HAVING COUNT(*) > 1;
```

Результат должен быть пустым.

---

## 12.2 DIM_MATERIAL

Бизнес-идентификатор материала:

```text
material_id
```

не должен иметь несколько актуальных записей, если это не предусмотрено моделью измерения.

Проверять отдельно:

- уникальность бизнес-ключа;
- корректность surrogate key;
- соответствие ODS.

---

## 12.3 DIM_WAREHOUSE

Для склада используется история изменений.

Если применяется SCD Type 2, проверять:

- бизнес-ключ склада;
- `date_from`;
- `date_to`;
- отсутствие пересекающихся периодов;
- наличие только одной актуальной версии для одного момента времени.

---

# 13. FACT_INVENTORY

Факт оборотной ведомости должен формироваться из ODS.

Перед загрузкой факта необходимо определить бизнес-зерно.

Для текущей реализации:

```text
период
+
склад
+
материал
```

то есть:

```text
date_key_start
date_key_end
warehouse_sk
material_sk
```

должны однозначно определять строку факта, если именно это является бизнес-ключом факта.

## 13.1 Критическая проверка

Нельзя просто использовать:

```sql
NOT EXISTS
```

и считать задачу решённой.

Сначала необходимо гарантировать, что источник SELECT сам не содержит несколько строк для одного бизнес-ключа.

Проверка:

```sql
SELECT
    date_key_start,
    date_key_end,
    warehouse_sk,
    material_sk,
    COUNT(*) AS cnt
FROM <источник_факта>
GROUP BY
    date_key_start,
    date_key_end,
    warehouse_sk,
    material_sk
HAVING COUNT(*) > 1;
```

Результат должен быть пустым перед INSERT.

Если источник содержит несколько версий одной записи, необходимо явно определить правило выбора версии.

Например:

```text
последняя дата выгрузки
```

Но такое правило должно соответствовать смыслу данных.

---

# 14. FACT_PRICES

Для цен также необходимо определить бизнес-зерно.

Текущая логика использует:

```text
date_key_start
+
date_key_end
+
material_sk
```

Проверяющий должен убедиться:

1. Что это действительно бизнес-зерно цены.
2. Что ODS не содержит несколько версий одного зерна.
3. Если содержит — определено правило выбора последней версии.
4. INSERT не создаёт дубликаты.
5. UNIQUE constraint соответствует бизнес-зерну.

---

# 15. SCD Type 2

SCD2 требуется только там, где необходимо хранить историю изменений измерения.

Не следует автоматически применять SCD2 ко всем таблицам.

Для каждого SCD2-объекта проверить:

```text
business_key
date_from
date_to
```

и правила:

- новая версия закрывает старую;
- периоды не пересекаются;
- текущая версия определяется однозначно;
- исторические версии не уничтожаются.

---

# 16. ETL Master

Главный оркестратор:

```sql
EXEC BI_DWH.etl.sp_etl_master;
```

Порядок выполнения:

```text
1. dim_date
      ↓
2. validation + quarantine
      ↓
3. ODS
      ↓
4. dimensions
      ↓
5. facts
      ↓
6. datamart
```

Проверяющий должен убедиться, что порядок действительно соответствует зависимостям.

Например:

```text
ODS должен существовать
до загрузки FACT.

DIM должен существовать
до загрузки FACT,
если FACT использует surrogate keys.
```

---

# 17. Логирование

Система должна логировать:

- имя процедуры;
- время начала;
- время окончания;
- статус;
- количество обработанных строк, если применимо;
- текст ошибки.

Минимальные статусы:

```text
RUNNING
SUCCESS
ERROR
```

При ошибке:

```text
TRY
 ↓
CATCH
 ↓
etl.etl_log
 ↓
THROW
```

Ошибка не должна быть молча подавлена.

---

# 18. SQL Agent

SQL Agent используется для регулярного запуска ETL.

Ночной запуск должен выполнять:

```sql
EXEC BI_DWH.etl.sp_load_staging_from_import;
EXEC BI_DWH.etl.sp_etl_master;
```

SQL Agent не должен содержать бизнес-логику ETL.

Он является планировщиком.

Бизнес-логика находится в хранимых процедурах.

---

# 19. startup.sh

`startup.sh` отвечает за запуск контейнера и первоначальную инициализацию.

Он может:

1. запустить SQL Server;
2. дождаться готовности SQL Server;
3. выполнить DDL/CREATE OR ALTER;
4. создать/обновить процедуры;
5. выполнить первоначальный ETL.

После этого основной долгоживущий процесс контейнера — SQL Server.

Ночная регулярная обработка выполняется SQL Agent.

---

# 20. Идемпотентность

Каждая ETL-процедура должна быть проверена на повторный запуск.

Тест:

```text
1. Запустить ETL.
2. Запустить ETL повторно.
3. Сравнить количество строк.
4. Проверить отсутствие новых дублей.
```

Повторный запуск без новых/изменённых данных не должен создавать новые факты.

---

# 21. Проверка проекта агентом

Проверку SQL-проекта выполнять по уровням.

## Шаг 1 — структура

Проверить:

- схемы;
- таблицы;
- процедуры;
- constraints;
- индексы;
- SQL Agent jobs;
- startup.sh.

## Шаг 2 — зависимости

Построить цепочку:

```text
startup
  ↓
SQL Server
  ↓
процедуры загрузки
  ↓
STAGING
  ↓
validation
  ↓
QUARANTINE / ODS
  ↓
DIM
  ↓
FACT
  ↓
DATAMART
```

Для каждой процедуры определить:

```text
что получает
что делает
что изменяет
что вызывает
что возвращает
```

## Шаг 3 — соответствие ТЗ

Для каждого требования найти конкретный код, который его реализует.

Формат проверки:

```text
Требование
→ файл
→ процедура
→ конкретная таблица/операция
→ результат проверки
```

Если реализация не найдена:

```text
FAIL — требование не подтверждено кодом
```

## Шаг 4 — тестирование

Минимальный набор:

### Первоначальная загрузка

```text
49 файлов
→ STAGING
→ QUARANTINE / ODS
→ DWH
```

Проверить количества.

### Повторный запуск

Запустить тот же ETL ещё раз.

Ожидается:

```text
новых дублей нет
```

### Новый файл

Добавить новый CSV.

Ожидается:

```text
обработан только новый файл
```

### Изменённый файл

Изменить существующий CSV.

Ожидается:

```text
изменение обнаружено
файл обработан согласно механизму инкремента
```

### Ошибочная строка

Добавить некорректное значение.

Ожидается:

```text
строка → QUARANTINE
корректные строки → ODS
ETL не теряет корректные строки
```

### Ошибка процедуры

Создать контролируемую ошибку.

Ожидается:

```text
etl.etl_log.status = ERROR
error_msg заполнен
ошибка не скрыта
```

# 23. Важное правило проверки

Нельзя считать проект корректным только потому, что:

```text
CREATE PROCEDURE
```

выполняется без ошибки.

Нужно проверить фактический поток данных.

Особенно важно проверять ситуации:

```text
один файл
несколько файлов
повторный запуск
изменённый файл
дубли внутри ODS
ошибочные строки
несколько версий одной бизнес-записи
SCD2
```

# 24. Формат итогового отчёта проверки

Агент должен выдавать результат в формате:

| Область | Статус | Что проверено | Проблема |
|---|---|---|---|
| Первоначальная загрузка | PASS/FAIL | ... | ... |
| Инкрементальная загрузка | PASS/FAIL | ... | ... |
| Реестр файлов | PASS/FAIL | ... | ... |
| STAGING | PASS/FAIL | ... | ... |
| QUARANTINE | PASS/FAIL | ... | ... |
| ODS | PASS/FAIL | ... | ... |
| DIM | PASS/FAIL | ... | ... |
| FACT_PRICES | PASS/FAIL | ... | ... |
| FACT_INVENTORY | PASS/FAIL | ... | ... |
| Логирование | PASS/FAIL | ... | ... |
| SQL Agent | PASS/FAIL | ... | ... |
| Идемпотентность | PASS/FAIL | ... | ... |

## Правила статусов

`PASS` — требование подтверждено кодом и тестом.

`FAIL` — требование нарушено или тест обнаружил проблему.

`WARN` — потенциальная проблема, которую невозможно подтвердить только имеющимся кодом.

`N/A` — требование неприменимо.

---

# 25. Приоритет проверки

Проверять в следующем порядке:

```text
1. STAGING / загрузка файлов
2. file_registry
3. QUARANTINE
4. ODS
5. DIM
6. FACT
7. инкрементальность
8. идемпотентность
9. логирование
10. SQL Agent
11. DATAMART
```

Если нарушен нижний слой, сначала исправлять его.

Например:

```text
STAGING работает неправильно
        ↓
не переходить сразу к исправлению FACT
```

Сначала необходимо обеспечить корректность:

```text
Файл → STAGING → QUARANTINE/ODS
```

и только после этого проверять:

```text
ODS → DIM → FACT → DATAMART
```
